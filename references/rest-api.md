# Rules through the REST API, and the component JSON

Jira Cloud has a public REST API that lists, reads, creates, updates and deletes automation rules. Rules can live as JSON in a repository and be written to a site by script, with the editor kept for review. Everything below was verified against live Cloud sites between August and November 2026 unless marked otherwise.

## The API

Base URL: `https://api.atlassian.com/automation/public/jira/<cloudId>/rest/v1`. Basic auth with an account email and a classic API token works. Spec: `https://dac-static.atlassian.com/cloud/automation/swagger.v3.json` (version 1.0.22 when checked).

| Call | What it does, and what bites |
|---|---|
| `POST /rule/summary` | Lists rules. Body `{"limit": 100, "scope": "ari:cloud:jira:<cloudId>:project/<projectId>"}`; answers `data[]` with `uuid`, `name`, `state`, `ruleScopeARIs`. |
| `GET /rule/<uuid>` | The whole rule under `rule`: `name`, `state`, `actor`, `authorAccountId`, `trigger`, `components`, `ruleScopeARIs`, `notifyOnError`, `writeAccessType`, `canOtherRuleTrigger`, `labels`, `collaborators`. |
| `POST /rule` | Creates a rule from `{"rule": {...}}` in the format GET returns. **Needs `authorAccountId`** (the caller's, from `/rest/api/3/myself`); without it the answer is a bare 400 "could not be parsed" with no hint. Answers with the new rule's `ruleUuid` (run, 2026-10). |
| `PUT /rule/<uuid>` | Replaces the rule. Send the live trigger back unchanged and it survives, including an incoming webhook's URL and secret. Set `state` here too. |
| `DELETE /rule/<uuid>` | Answers **415** unless the request carries `Content-Type: application/json`; send `{}` as the body. |
| `PUT /rule/<uuid>/state` | Switches a rule on or off without touching the rest: `{"value": "ENABLED"}` or `"DISABLED"`. |
| `POST /rule/manual/<ruleId>/invocation` | Runs a manual-trigger rule, which makes manual rules testable by script: `{"objects": ["ari:cloud:jira:<cloudId>:issue/<issueId>", ...], "userInputs": {"<variableName>": {"inputType": "TEXT", "value": "..."}}}`; inputs are keyed by the prompt's `variableName`, and a dropdown takes one of its options as `value`. Up to 50 objects, all from one space. Input types: `TEXT`, `PARAGRAPH`, `DROPDOWN`, `NUMBER`, `BOOLEAN`. |
| `POST /rule/manual/search` | Lists the manual rules available for an object. |

There is **no audit log endpoint**: why a run failed is visible only in the rule's audit log in the editor, or in the owner's error mail. Nor is there a validation or dry-run call: a rule is checked only by writing it, so write it disabled.

- **The JSON is the export format.** What `GET /rule` returns is what the editor's export produces. On create, leave out `uuid`, `created`, `updated` and the component ids.
- **Rule-level keys** (read back, 2026-10). `"actor": {"type": "ACCOUNT_ID", "actor": "<accountId>"}` is the user the rule runs as; *Automation for Jira* read back as `557058:f58131cb-b67d-43c7-b30d-6b58d40bd077` (an Atlassian app account, seen on one site). `authorAccountId` is the rule's owner, who gets the error mails, so hand ownership over with the rule. `notifyOnError` read back as `"FIRSTERROR"`. `canOtherRuleTrigger` is *Allow other rules to trigger this rule* and belongs on the rule being triggered: a rule with it `true` fires on another rule's field write even when the writing rule has it `false` (run, 2026-11).
- **Comparing a rule with its JSON:** drop `id`, `parentId`, `conditionParentId` and `connectionId` on both sides, which the API adds or changes. In jq: `walk(if type == "object" then del(.id, .parentId, .conditionParentId, .connectionId) else . end)`.
- **`GET` hands out the webhook secret.** An incoming-webhook trigger comes back with its `webhookToken` in clear text. Filter it out of anything you print, log or commit.
- **Keep secrets out of your tooling.** Create a webhook rule in the editor with only its trigger, so the editor generates URL and secret and a person stores them. Then `PUT` the steps onto it, echoing the trigger as read.
- **Create rules disabled** (`"state": "DISABLED"`) and let a person switch them on after reviewing them in the editor.
- **A rule across several spaces** takes several project ARIs in `ruleScopeARIs`. Jira then sets the trigger's `eventFilters` to every space in the scope, whatever you sent, and keeps its own order. So the trigger listens in all of them, and a comparison has to treat `eventFilters` as a set. To act in one space only, start the steps with a JQL condition `project = <KEY>` (run, 2026-11). Only a user with **Administer Jira** can create or edit a rule scoped beyond one space (docs, checked 2026-10).
- **Error answers are thin.** A rule with only a trigger gets 400 "Automation rule must contain at least one valid condition or action"; one with only conditions, 400 "...at least one valid action". A malformed component usually gets a **500 with an empty body**. Find it by bisecting: post disabled throwaway rules with the first *n* components, delete each one created, and the first *n* that fails names the culprit.
- **Editor deep link** (seen on a service space): `https://<site>.atlassian.net/jira/servicedesk/projects/<KEY>/settings/automate#/rule/<uuid>`. The path segment is `automate`, not `automation`. An optional `/<componentId>` at the end selects a step.

## Finding a component's JSON: the probe rule

Atlassian documents the endpoints but not the shape of each component's `value`, and a wrong guess gets the same opaque "could not be parsed". When a component is missing from the catalogue below, have someone build a throwaway rule in the editor holding that component with dummy values, saved **disabled**. Read it with `GET /rule/<uuid>`, copy the shapes, delete the probe. That takes minutes; guessing takes hours.

## Component catalogue

`component` is `TRIGGER`, `CONDITION`, `CONDITION_BLOCK`, `BRANCH` or `ACTION`. A branch sent as `ACTION` gets the empty 500. Shapes are trimmed to the keys that matter; send `schemaVersion` as shown.

### Triggers

| `type` | `schemaVersion` | `value` |
|---|---|---|
| `jira.manual.trigger.issue` | 3 | `{"inputFromUsers": true, "inputPrompts": [{"inputType": "DROPDOWN", "displayName": "who", "required": true, "variableName": "varWho", "defaultValue": ["A", "B"]}, {"inputType": "TEXT", "displayName": "email", "required": true, "variableName": "varEmail", "defaultValue": ""}], "groups": [], "issueFilter": null, "jQLFilter": null}`. A dropdown's options sit in `defaultValue`. Read inputs as `{{userInputs.varWho}}`. The editor offers short text, paragraph, dropdown, number and checkbox; the spec's input types are `TEXT`, `PARAGRAPH`, `DROPDOWN`, `NUMBER` and `BOOLEAN`. `TEXT`, `DROPDOWN` and `PARAGRAPH` have been read back from live rules, and a rule with all three, one `TEXT` with `"required": false`, was created through the API and run (2026-11). A `DROPDOWN` with `"required": false` was too: invoked without that input, `{{userInputs.<variableName>}}` renders empty, a text-field `SET` operation with it leaves the field empty, and `{{#if(userInputs.<variableName>.isNotEmpty())}}…{{/}}` skips its text (run, 2026-11). Whether the editor's prompt lets a person clear an optional dropdown again once picked is not checked. `groups` is the editor's *Groups that can run trigger*. The rule shows as an entry in the **Actions** menu of every work item in its scope. There is no date input, and to write a dropdown answer into a select field the field's options must match the dropdown's (docs, [KB](https://support.atlassian.com/jira/kb/how-to-link-a-custom-field-with-the-prompt-action-input-with-manual-triggers-in-jira-automation/)). |
| `jira.incoming.webhook` | — | Keys `jql`, `searchOrProvide`, `webhookToken`. `searchOrProvide: "none"` is the editor's "No work items from the webhook"; `"provided"` expects work items in the POST body. Payload fields read as `{{webhookData.<key>}}`. A trigger new from the editor reads back as `"provided"`; switch it to `none` for a payload-only rule. Call it with `POST <webhook URL>` and the headers `X-Automation-Webhook-Token: <secret>` and `Content-Type: application/json`. The answer is a 2xx at once and the rule runs afterwards, so a test polls for the effect (up to 90 s allowed; run, 2026-10). |

The time zone lives in the `TZID` of the RRULE. |

With the wrong spelling the rule is saved and simply never fires. A change made by a transition's post function counts. `VALUE_ADDED` fires when the field goes from empty to a value; emptying it does not fire it, so a rule can clear its own trigger field as its last step and fire again on the next write (run, 2026-11). |
| `jira.issue.event.trigger:commented` | 1 | `{"eventTypes": ["PRIMARY_ACTION"], "eventFilters": ["ari:cloud:jira:<cloudId>:project/<projectId>"]}` |
| `jira.issue.event.trigger:created` | 1 | `{"eventKey": "jira:issue_created", "issueEvent": "issue_created", "eventFilters": ["ari:cloud:jira:<cloudId>:project/<projectId>"]}` |

**Trigger conditions.** The trigger object has its own `conditions` array, which the editor shows inside the trigger node. Filter on the triggering work item's fields there, instead of in a separate condition step:

```json
"trigger": {
  "component": "TRIGGER", "schemaVersion": 1, "type": "jira.issue.event.trigger:created",
  "value": {"eventKey": "jira:issue_created", "issueEvent": "issue_created", "eventFilters": ["ari:cloud:jira:<cloudId>:project/<projectId>"]},
  "conditions": [
    {"component": "CONDITION", "schemaVersion": 3, "type": "jira.issue.condition",
     "value": {"selectedField": {"type": "ID", "value": "issuetype"}, "selectedFieldType": "issuetype", "comparison": "EQUALS",
               "compareValue": {"type": "ID", "modifier": null, "value": "<work type id>", "multiValue": false, "source": null}},
     "conditions": [], "children": []}
  ]
}
```

Written by the editor (read back, 9 Nov 2026). Several entries in the array must all hold. The `jira.issue.condition` variants in the next table work here too.

### Conditions and If/else

| `type` | `schemaVersion` | `value` |
|---|---|---|
| `jira.comparator.condition` | 1 | `{"first": "{{lookupIssues.size\|0}}", "second": "0", "operator": "EQUALS"}` (smart values condition) |
| `jira.jql.condition` | 1 | the JQL as a plain string |
| `jira.issue.condition` | 3 | Work item fields condition. `{"selectedField": {"type": "ID", "value": "status"}, "selectedFieldType": "status", "comparison": "NOT_ONE_OF", "compareValue": {"type": "NAME", "value": "[\"Open\",\"Closed\"]", "multiValue": true}}`; the list is a JSON-encoded string. Read back from editor-written rules: `comparison` `EQUALS`, `NOT_EQUAL` and `ONE_OF` on `status` (value by `NAME` or `ID`), `EQUALS` on `issuetype` by `ID`, `CONTAINS_ANY` on `labels` (`{"type": "NAME", "value": "[\"a\"]", "multiValue": true}`). Single values carry `"multiValue": false`. Prefer this over a smart-value comparison on `{{issue.<field>}}`, and put it on the trigger when it filters the triggering work item. |
| `jira.user.condition` | 6 | `{"conditions": [{"field": "initiator", "check": "NOT_IN_ROLE", "criteria": [{"type": "NAME", "value": "Service Desk Team"}]}], "operator": "OR"}` |

**If/else** is one `CONDITION` of type `jira.condition.container.block` with `value: {}`. Its `children` are `CONDITION_BLOCK`s of type `jira.condition.if.block`, `value: {"conditionMatchType": "ALL"}`, each holding its conditions in `conditions` and its actions in `children`. The **else** is one more `jira.condition.if.block` whose `conditions` list is empty.

Delivery to the role's members is not observed yet. |

### Field operations

Each entry in `operations` is `{"field": <ref>, "fieldType": "<type key>", "type": "SET", "value": <value>}`. The field reference is `{"type": "ID", "value": "customfield_<n>"}` or `{"type": "NAME", "value": "<field name>"}`; the editor writes either, and the ID survives a rename. Custom field type keys start with `com.atlassian.jira.plugin.system.customfieldtypes:`, shortened to `…:` here; read a field's key from `GET /rest/api/3/field` (`schema.custom`).

| Field type (`fieldType`) | `value` | Source |
|---|---|---|
| `summary`, `description`, `…:textfield`, `…:url` | a string with smart values, e.g. `"{{issue.key}}: {{webhookData.fullName}}"`; `\n` for line breaks. A multi-line paragraph field copied as `"{{issue.customfield_<n>}}"` keeps its line breaks in `description` (run, 2026-11), unlike `jsonEncode` in advanced JSON | editor and API, read back, run |
| `…:textarea` (paragraph) | a string, as above; `\n` in the value stores real line breaks | API, run (2026-11) |
| `…:datepicker`, `duedate` | a smart value. A `yyyy-MM-dd` string works on both (`"{{webhookData.startDate}}"`, `"{{now.convertToTimeZone(\"America/Los_Angeles\").jiraDate}}"`; API, run). A smart value that renders empty leaves the field empty, and the create still succeeds without an error (run, 2026-10). The editor also writes a bare date object for Due date (`"{{now.plusBusinessDays(5)}}"`); for a custom date picker add `.jiraDate` until the bare form is seen to work there | editor and API, run |
| `…:datetime` | `"{{now.convertToTimeZone(issue.reporter.timeZone)}}"` | editor |
| `…:select` | the option by name: `{"type": "NAME", "value": "<option name>"}`, or a smart value that renders an option name: `{"type": "SMART", "value": "{{userInputs.<input>}}"}` (a manual trigger's dropdown answer, written through the API and run, 2026-11) | editor; API, run (2026-11) |
| `labels` | `[{"type": "FREE", "value": "my-label"}]` | editor |
| `assignee` | `{"type": "ID", "value": "<accountId>"}`, or `{"type": "COPY", "value": "trigger"}` | editor |
| `project`, `issuetype` | `{"type": "ID", "value": "<id>"}` | API, read back |
| `security` (field reference `{"type": "ID", "value": "security"}`) | the level by name: `{"type": "NAME", "value": "<level name>"}`, or a smart value that renders a level name: `{"type": "SMART", "value": "{{levelName}}"}` (the editor's Security Level box takes a typed smart value) | editor, read back, run (2026-11) |
| `issuelinks` (field reference `{"type": "ID", "value": "issuelinks"}`), *Linked work items* on Create | `{"issue": {"type": "COPY", "value": "trigger"}, "linkType": "inward:10003"}`: the work item to link to (here the trigger work item) and `<direction>:<link type id>`. Read the ids from `GET /rest/api/3/issueLinkType` (10003 was "Relates" on that site). Replaces `"update": {"issuelinks": [{"add": …}]}` in advanced JSON | editor, read back, run (2026-11: the link is found by `issue in linkedIssues("<KEY>-<n>")`) |
| `com.atlassian.servicedesk:vp-origin` (Request Type; field reference by name, `{"type": "NAME", "value": "Request Type"}`) | **not settable here.** The editor refuses it in Create and Edit: "Request type can't be edited here. You will need to use the 'Edit request type' action instead." An operation added anyway reads back `"value": null` and sets nothing; leave it out. Use the *Edit request type* action (`jira.edit.request.type` in the action table, first in a `created` branch; run, 2026-11), or `{"fields": {"customfield_<n>": "<request type id>"}}` in the create step's `advancedFields`, which is proven | editor message, read back |

**Copying a field** is a different operation type, not `SET`: `{"field": {"type": "NAME", "value": "<field name>"}, "fieldType": "…:select", "type": "COPY", "value": {"copyOptions": [], "sourceIssue": "current", "sourceField": {"type": "NAME", "value": "<field name>", "fieldType": "…:select"}}}`. `sourceIssue: "current"` is the work item the step runs on, which in a rule's trunk is the trigger work item. It copies the option as it is, so a select needs no `{{….value}}` round trip (editor, read back, run 2026-11). The editor writes field references by `NAME` or by `ID` from one field to the next; both work, and only `ID` survives a rename.

Not on record as operations yet: reporter, request participants, clearing a field. All three are proven in `advancedFields` (run, 2026-11): the reporter as `{"fields": {"reporter": {"id": "{{customer.accountId}}"}}}`, and clearing as `{"fields": {"customfield_<n>": null}}` (select, text and paragraph fields). Request participants are proven in `advancedFields` as well (run, 2026-11): `{"update": {"customfield_<participants field>": [{"add": {"id": "{{customer.accountId}}"}}]}}`, right after an *Add service project customer* step for that address in the same branch. The field must be on the work item's edit screen, like any field automation sets; a service space that hides participants from its agents needs a screen of its own for the work items the rule edits. Probe the operation shapes before converting.

**When converting a step in the editor, empty *More options → Additional fields*.** Choosing a field in *Choose fields to set* leaves the old JSON in place, and the rule then sets that field twice (read back from a live rule).

## Reading results back by script

- **The customer list includes the space's agents.** `GET /rest/servicedeskapi/servicedesk/<id>/customer?query=<email>` returns an agent of that service space although nobody added them as a customer (read back, 2026-11). A check that an address is *not* a customer of some space proves nothing for an agent address; record the answer before the run and judge only addresses that were not listed then.
- **Issue keys in rule-written text come back as smart links.** A key a rule writes into a rich-text field or a comment is stored in ADF as an `inlineCard` whose `attrs.url` ends in `/browse/<KEY>-<n>`, not as a text node. A test that joins the `.text` nodes from REST v3 loses the key; read it from the card's URL (run, 2026-11). Only a key standing on its own becomes a card: `in {{triggerIssue.key}}:` stored a card, `A={{triggerIssue.key}}` stayed text (run, 2026-11).
